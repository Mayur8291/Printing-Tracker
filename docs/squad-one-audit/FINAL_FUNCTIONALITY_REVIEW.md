# Final functionality parity review

This independent implementation review compares the approved local Flutter `origin/develop` commit `5d55d9461af18b94a867dce07dee7c4b76f1e51f`, the pinned Rails source and reviewed WMS differences, the 115 workflow rows in `functionality-matrix.csv`, and the integrated backend through migration `20261108090719`. It is not a production-release or cutover approval. A function name existing is only a routing check, not evidence that every behavior is correct.

The actual local PostgreSQL catalogue contains all 115 originally planned RPC names. Public wrappers are generated dynamically, so a text search for `CREATE FUNCTION canto_api...` incorrectly reports many implemented contracts as missing. Edge/native/worker workflows are outside that RPC count and were reviewed separately. SDK and deployed release acceptance remain the parent integration lane's responsibility.

## Concrete findings

1. **PC selling amounts were a genuine parity gap, now fixed locally.** Source role lists separately authorize Production Coordinator selling prices and exclude payment information. Migration `90719` corrects the shared projections without broadening rows or payment authority. Fourteen new tests include a complete customer→SC→PC→FM→cutter→inspector→dispatch→rating journey. See [source evidence and financial policy review](PERSONA_FINANCE_PARITY_REVIEW.md).
2. **Automatic weekly tailor reports were a genuine scheduling gap.** Manual document generation and configured mail recipients already existed, but DOC.04 and OPS.03 also require automatic Saturday enqueue. The parent assigned this correction to the business-mail lane; it is outside the frozen `90719` review prefix. Source `config/sidekiq.yml` schedules `WeeklyTailorReportJob` with `1 0 * * 6`; `app/jobs/weekly_tailor_report_job.rb` calls `WeeklyTailorReportService`. That service computes the previous Saturday–Friday period, iterates Tailor subjects and invokes the shared statistics/PDF/mail path. The approved matrix requires an explicit Kolkata schedule and authorized recipients. The correction must use bounded, repeat-safe enqueue through the existing worker heartbeat, rather than introducing a second document implementation.
3. **Support impersonation is intentionally disabled, not an accidental missing route.** AUTH.06 explicitly retires universal-password login-as and says not to implement impersonation before an explicit support policy. The main plan's `squad-account` route table says the same. Existing scoped people/order views support administrative inspection; an unrestricted support-session token must not be created merely to satisfy a route-name count.
4. **Reserve/release/fulfill do not require duplicate inventory services.** INTEGRATE.01 is fulfilled through provider-native order operations, cancellation, status/fulfillment evidence and the shared dealer ledger. The reviewed Dashboard helper classes do not establish a second independent business reservation API. See [warehouse ownership and adapter decisions](WAREHOUSE_IMPLEMENTATION.md). Provider environment configuration and actual sandbox acceptance are still required.
5. **Mixed concurrent performance exposed and corrected a real implementation bottleneck.** Earlier measurements explicitly tested warm individual queries. The new four-connection, 400-call workload found assignment/inspection/dispatch above the500ms budget because child RLS repeatedly enumerated entire factory histories. The focused `93050` point-policy correction preserves current authority and passes all ten measured RPC budgets, committed contention checks and519 affected regression tests. See [measurement, query plans and limits](MIXED_WORKLOAD_PERFORMANCE.md). This remains local database evidence, never a claim about mobile/network latency or hosted provider throughput.

No further concrete missing implementation was identified in this pass. This statement does not replace the complete regression suite, row-specific acceptance binding, real-provider acceptance, or the final hosted persona journeys.
