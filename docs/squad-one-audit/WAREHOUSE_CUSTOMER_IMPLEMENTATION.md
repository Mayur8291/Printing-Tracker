# Warehouse customer synchronization

Local implementation is ready for integration in migration `20261108083543_squad_warehouse_customers.sql`. **25 new customer tests pass**, and the preceding complete warehouse regression run passed 95 tests before the last four customer cases were added. No hosted provider mutation, production change or ownership activation was performed by this lane.

One shared customer workflow covers profile, admin person edits, address save/archive, approval, disable/enable and archive changes. Fanout happens only when a verified ownership epoch and the selected Uniware provider are enabled. Dashboard customer details remain inline on order requests; this does not invent a standalone Dashboard customer API.

The payload matches the pinned Rails `UniCommerce::CreateOrUpdateCustomerService`: deterministic environment-prefixed customer/contact codes, company-name fallback, current email/phone/GST, and primary billing/shipping address with the same state-code mapping. Selection is deterministic when legacy primary-address data ties. Missing required address/contact fields fail before HTTP. New-side disabled/deleted/unapproved customers are sent as disabled. Existing conflicting provider IDs require reconciliation rather than being overwritten.

The existing `warehouse_operations` ledger stores customer ID, frozen request body, create/edit action, stable request key, prior-attempt marker, exact prepared lease and provider acknowledgment. Current actor/customer authority is checked before each external attempt. Customer events serialize by customer ID: later edits wait for a live earlier operation and then capture the latest profile. An uncertain dead earlier create blocks subsequent creation visibly. A first Uniware order without a confirmed customer code creates a durable customer dependency and waits; it never fabricates a code and reports order submission before that dependency succeeds.

Successful HTTP confirmation persists only the exact customer code through a narrow lease-backed `integration_customer_context` capability. That role can update only the confirmed customer's provider-code column and timestamp; it cannot edit passwords, roles, profile fields or another customer. If the initiating actor loses authority after HTTP, the observed provider identity can still be recorded without pretending that actor remains authorized. A provider/configuration/identity mismatch retains proof and requires reconciliation.

The Edge adapter intentionally has no blind customer retry after an uncertain create/edit because the current verified Uniware contract provides no customer GET/adoption endpoint. A verified `mutation_attempted: false` result may reset the first attempt only under the same prepared lease when no earlier attempt existed; a later token failure cannot erase an earlier uncertain mutation. Exact finish retries are idempotent. Generation, ownership, provider and lease fences apply throughout. Local provider-code publication advances edit revision and adds audit without recursively generating another customer event.

Public endpoints remain the existing service-only `squad_warehouse_prepare` and `squad_warehouse_finish`; no new browser RPC or Edge deployment is added. Old preparation/finish implementations are retained as private base functions for submit/reconciliation/inventory, preserving one implementation of those behaviors.

Tests cover source-shaped create/edit payloads, current primary address, missing fields, foreign scope, disabled actors before/after HTTP, confirmed identity persistence, wrong/missing proof, stale generation/lease, provider change, frozen retries, pre-mutation retry distinction, concurrent profile ordering, first-order dependency, Dashboard inline behavior and mirror suppression. Production-shaped hosted provider acceptance and amendment/cancellation sagas remain separate integration work.
